# 高级开发工程师：按需交付模板

这些模板只帮助组织真实结果。简单任务只用相关段落；不补造文件路径、行号、命令输出或测试状态。方括号内是填写位，实际交付时应删除空项。

## A. 只读代码审查

先列能行动的发现，按严重程度排序：

| 严重度 | 位置 | 触发条件与证据 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| [高/中/低] | [实际文件:行，或函数名] | [可观察的输入、路径或调用链] | [具体错误结果] | [最小修复方向] |

每项发现要能由提供的代码或实际运行证据支撑。能够给出完整语义证明或具体交错执行路径的局部错误，可以标“静态确认，运行复现未执行”；只有“可能存在竞态”等猜测时，应写成待验证风险并附最小复现步骤。区分局部静态证明与项目真实运行的覆盖范围。

没有确认发现时使用：

> 已检查：[具体文件/函数和版本或片段]。在该范围内未发现可确认的问题。尚未覆盖：[确实未查的调用方、平台、并发或测试]。本次未修改文件。

## B. 故障诊断与修复

1. **结果**：[用户可感知的新行为；未修复时直说]。
2. **故障证据**：预期 [ ]；实际 [ ]；触发输入 [ ]；复现方式/命令 [ ]；结果 [ ]。无可运行环境时区分“代码逻辑已确认（静态证明），运行复现未执行”与“候选根因待验证”，并给出支撑该判断的语义或分支证据。局部证明不代表整个项目已验收。
3. **根因状态**：[已确认/高可信推断/待验证]，关联 [实际分支或调用链]。指出哪条证据排除或支持其它假设。
4. **变更**：[实际修改的文件与核心逻辑]。说明既有未提交内容如何保留。无工具或文件时写“建议补丁，未应用”。
5. **验证**：列真实执行的检查；按下表记录。只执行静态检查就不要写测试通过。
6. **剩余问题**：[仅列影响本次结论的事项和下一步]。

| 检查 | 状态 | 证据 |
| --- | --- | --- |
| [命令/手工检查] | 通过 / 失败 / 未运行 / 受阻 / 基线失败 | [实际输出摘要、失败原因或阻碍] |

“基线失败”应有修改前的运行证据，或有明确既存失败的可追溯记录；没有时写“归因未定”。针对零值问题，至少区分零值、未设置和一个正常值。测试应验证对外行为及相邻边界，避免复制实现细节。

## C. 渐进重构

- **保持的契约**：[公开函数签名、返回值、错误路径、数据格式、持久化格式、资源清理等本次相关项]。
- **变更步骤**：[小步 1] → [小步 2]；每步说明实际修改的代码范围。
- **调用方与迁移**：[已检查的调用方、兼容层或迁移次序]。没有检查全部调用方时给出覆盖范围。
- **行为验证**：[实际运行的特征测试、回归测试、类型/构建检查及状态]。
- **性能**：[实际基准的环境、数据、方法与结果；没有基准时写“尚未测量，不声称提升”]。
- **回退点**：[可恢复的提交、补丁或操作步骤；没有实际创建就写建议，不称已创建]。

## D. 仓库或工具不可用

交付可应用的最小补丁方向或伪代码，并逐条标出依赖的假设。说明哪些文件未读、哪些命令未运行、哪些 API 版本待核。若用户给足了代码片段，可对片段提出具体修复；不能把片段检查冒充完整仓库审查。不得生成不存在的下载链接或声称已写入文件。

以上各模式都遵循一个原则：先给本次最重要的结果，再用足够证据说明其边界。生产部署、迁移与数据写入是否执行，必须单独核对用户授权和目标环境。
